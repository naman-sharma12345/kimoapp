# Accessibility validation

The target is WCAG 2.2 AA. Automated Axe checks and keyboard behavior tests supplement, rather than replace, assistive-technology testing.

## Implemented

- Semantic page/landmark headings, skip link and route focus on the heading or composer/main fallback. Dialog focus traps and named icon buttons use existing Radix components. Palette and programmatic sign-in dialogs restore the opener explicitly.
- Keyboard Studio selection, trim, split, duplicate, move, delete, undo/redo, timeline controls, caption fields, playback, palette search and compare range. Historical cuts expose a read-only preview and do not consume edit history.
- Palette arrows keep the selected result visible without moving focus away from the combobox. Touch focus transfers from the initial lightweight composer into its loaded editor.
- Reduced-motion paths retain useful static progress; high-contrast preference raises cream-60 to cream-100 and line to line-strong. Native form elements retain forced-colors behavior.
- Privacy inline links are underlined. Small privacy text uses existing cream-60 instead of cream-38, following the earlier contrast decision. Review overlay copy uses cream-100 where its composited background otherwise failed Axe.
- Timecodes/counters use tabular numerals. Long names remain available through title text and accessible names. No change to the supplied logo or the user's requested removal of the composer resize grip/focus highlight.

## Automated evidence

`e2e/launch.spec.ts` checks landing, privacy, quota/sign-in, palette, export review and delivery, plus all five requested viewport sizes. Existing suites cover shared components, uploads, warm-up, Studio/manual editing, agent panel, render failures and expiry. `e2e/visual-launch.spec.ts` records controlled route/state baselines. Exact executed commands/results are recorded in `PHASE_LOG.md`; do not infer an unexecuted browser from the existence of a test.

Cream-60 over ink-1 meets the 4.5:1 body-text threshold (the automated Axe contrast pass is the acceptance evidence). Decorative waveform/timeline ticks and disabled controls have different contrast requirements from body text. The source design's low-opacity values are not automatically suitable for readable prose.

## Manual assistive-technology gates

**VoiceOver/macOS: not run.** This executor is Windows; WebKit automation is not VoiceOver or an actual Safari 18 run.

**NVDA: not run.** NVDA is not installed on this executor. No fabricated screen-reader transcript or blanket WCAG certification is recorded.

Before release, complete and record both passes:

1. From a fresh landing visit, navigate by headings/landmarks, describe a video, attach files and submit. Verify upload/progress announcements are useful without repeating every frame.
2. In Studio, find the agent composer, send an interrupt, navigate timeline clips, edit captions and use undo. Confirm the active action/selection and reconnect state are announced.
3. Open/close the palette and auth dialog. Verify focus returns to the opener, arrows announce visible results, and historical cuts announce their read-only state.
4. Complete review, cancel/retry a render, then use the delivery player/download/share with keyboard only. Verify expiry disables only edit-again.
5. Repeat at 200% zoom, reduced motion, increased contrast, Windows forced colors, and touch keyboard on a real iPhone. Record OS, browser, AT version, results and any fixes here.

These are outstanding manual environment gates, not backend dependencies. They must be completed before asserting the full WCAG acceptance checkbox.
